# Запуск и восстановление сервера 0.3

Реализованы API, worker и бот. Для реального использования нужны сессия E-Hentai,
bot token, права в канале и проверенный HTTPS на VPS. Эти данные не включены в поставку.

## Локальный запуск

```sh
uv sync --locked --extra source
cp .env.example .env
# Настройте owner/channel ID, точный origin расширения и EHTG_BOT_TOKEN.
uv run --locked --extra source ehtg migrate
uv run --locked --extra source ehtg source probe
uv run --locked --extra source ehtg source import-cookies /private/cookies.txt
uv run --locked --extra source ehtg check-telegram
```

Cookies импортируются только серверной командой после проверки. Старый рабочий
файл сохраняется при ошибке. Затем установите `EHTG_SOURCE_ENABLED=true` и запустите
три отдельных процесса из каталога backend:

```sh
uv run --locked --extra source uvicorn ehtg.api.app:create_app --factory --host 127.0.0.1 --port 8000 --no-access-log
uv run --locked --extra source ehtg worker
uv run --locked --extra source ehtg bot
```

`worker --once` исполняет до одного анализа и одного задания. `--analysis-only`
отключает отправку в Telegram для диагностического запуска. Без настроенного bot
token worker выполняет только анализ. Бот использует собственный асинхронный клиент
официального Bot API; aiogram из исходного ТЗ был рекомендацией, а не зависимостью.

В личном чате владельца `/help` показывает команды. Основной путь: ссылка → анализ →
карточка → `/pages ID REV ...` при необходимости → кнопка подтверждения или
`/publish ID REV`. `/pair` выдаёт одноразовый код, `/devices` и `/revoke DEVICE`
управляют устройствами. Бот не принимает настройки сессии и канала из сообщений.

## Контейнеры

`Dockerfile` и `compose.yaml` — подготовленная схема приложения без HTTPS-прокси.
Она не выбирает свободный порт на VPS автоматически и не меняет 3x-ui.
Порт API привязан к `127.0.0.1:8080`; сначала проверьте, что он свободен.
Все три процесса используют один постоянный том `data`, включая SQLite и OS locks.
Не разносите их по независимым томам или сетевым файловым системам.

Создайте `secrets/` и `imports/`, доступные UID/GID 10001; для секретов используйте
каталоги 0700 и файлы 0600. Поместите cookie jar в `imports/cookies.txt` через SSH.
В `.env` оставьте относительные пути из примера; в allowed hosts включите
`127.0.0.1`, `localhost` и фактический HTTPS-host.

```sh
docker compose build
docker compose --profile admin run --rm admin migrate
docker compose --profile admin run --rm admin source import-cookies /app/imports/cookies.txt
docker compose --profile admin run --rm admin check-telegram
# После успешных проверок и включения SOURCE_ENABLED:
docker compose up -d api worker bot
```

Настройка reverse proxy, сертификата, портов VPN и замеры нагрузки описаны в
`../../docs/deployment-options.md`. Перед внешним доступом выполните обследование.
Начальные лимиты Compose: API 192 MiB, worker 512 MiB, бот 128 MiB и доли CPU;
это настройки для проверки, а не результаты замеров на VPS.

## Состав и подписи

`PATCH /api/v1/drafts/ID` принимает `page_selection` и необязательный полный объект
`options`: `title`, `caption`, `removed_tags` (`namespace:value`),
`disable_notification=true`, `has_spoiler=false`. `caption` заменяет описательную
часть; название, число страниц, источник и номера части остаются в серверном шаблоне.
`null` возвращает автоматическое значение. Полный предпросмотр — `preview.parts`;
`hidden_tags` сообщает число убранных из-за лимита hashtags. Обязательные поля не
усекаются: слишком длинная подпись требует ручного исправления.

Подтверждение копирует весь план в задание. Редактирование требует свежий `If-Match`.
Базовые параметры не меняют уже подтверждённые задания. Десять страниц образуют
альбом; остаток из одной страницы отправляется отдельным фото. Сохраняются все
исходные позиции, включая одинаковые изображения.

Batch: `POST /batches` с `source_urls`; `PATCH /batches/ID` с упорядоченными `draft_ids`;
`POST /batches/ID/publish` с `items=[{id,revision},...]`. Изменение/подтверждение
требуют ревизию списка; подтверждение также требует `Idempotency-Key`. Ошибка
любой строки откатывает весь список заданий. Ссылки `/s/` разрешаются через `gtoken`
в фоновой работе и создают черновик всей галереи, а не публикацию одной картинки.

Повтор создаётся явно через `POST /jobs/ID/repost` или `/repost JOB`, после завершения
старого задания, и снова требует анализа и подтверждения. Активные задания одной
галереи не дублируются. Связи версий доступны в `snapshot.parent_url`; сведения о
предыдущем задании — в `duplicate`. Новая версия требует отдельного подтверждения.

## Остановка и неопределённая отправка

`POST /queue/pause` останавливает новые действия. `/queue/resume` продолжает очередь.
`POST /jobs/ID/cancel` и `/retry` требуют ревизию задания из `GET /jobs/ID`/его ETag.
Отмена не удаляет уже отправленные сообщения. Если HTTP-отправка уже началась,
сохраняется её фактический результат, после чего новые части не отправляются.

Перед отправкой каждая часть записывается в `publication_parts` как `sending`.
Успешный ответ и счётчики фиксируются одной транзакцией. Падение процесса в этом
интервале, таймаут после возможной отправки или HTTP 5xx переводят задание в
`needs_review`. Очередь удерживает его место; автоматического повтора нет.

Сверьте канал, номер части, исходные страницы и время попытки в `GET /jobs/ID` или
`/status JOB`. Затем `POST /jobs/ID/review` с If-Match:

- `{"decision":"sent","evidence":"ссылка или описание проверки"}` — считать отправленным;
- `{"decision":"not_sent"}` — разрешить повтор именно этой части;
- `{"decision":"cancel"}` — остановить дальнейшую отправку.

В боте: `/review JOB REV sent ссылка` либо `/review JOB REV not_sent`.
При ручном признании отправки неизвестные message IDs не выдумываются; сохраняется
доказательство владельца. Уже подтверждённые части повторно не отправляются.

Анимация останавливает задание до первой отправки. Предпросмотр:
`GET /jobs/ID/pages/INDEX/preview` либо `/preview JOB PAGE`. Явные решения:
`review` с `decision=first_frame`/`exclude` и `page=INDEX`; в боте `/frame` и `/exclude`.
Исключение пересчитывает план, пустой отбор запрещён. Изменившийся источник требует
отменить задание и создать новый предпросмотр. Слепой `/retry` это не обходит.

При квоте/потере сессии общая работа источника приостанавливается. После импорта
рабочей сессии `ehtg source resume` проверяет её и возобновляет связанные задания.
Telegram 429 сохраняет `retry_after` в БД; ожидание не блокирует API и бот.

При обновлении с прототипа 0.2 старые задания без сохранённого плана получают
`PUBLICATION_RECONFIRM_REQUIRED`. Отмените старое задание, создайте новый черновик
через `/repost JOB`, проверьте подпись и подтвердите. Автоматическая отправка
непросмотренных подписей при обновлении исключена.

## Файлы, уведомления и backup

Файлы: `files_path/JOB/NNNN.source`, `NNNN.photo`, `manifest.json`; хеши, размеры
и преобразования также в БД. Готовность после рестарта проверяется по файлу и SHA-256.
HTML и повреждённые/неподдерживаемые изображения не принимаются. Декодирование
изолировано по времени/памяти/числу пикселей, скачивание — по размеру и свободному диску.
На Linux также действуют RLIMIT и завершение дочернего процесса при смерти родителя.

JPEG/PNG/WebP преобразуются в JPEG на белом фоне с EXIF-ориентацией. Высоким/широким
страницам добавляются поля; содержимое не обрезается. Длинная сторона ограничена
4096 px, сумма сторон — 10000, отношение — 20, файл — 9.5 MB. Качество пробуется
92/85/75; дальнейшее уменьшение на 20% ограничено пятью шагами и длинной стороной
не ниже min(1280, исходная). Неподходящий результат останавливает задание.

Успешные файлы удаляются через 24 часа при обслуживании worker (ежечасно) или
`ehtg cleanup`; история/журнал остаются. Ошибочные и отменённые задания сохраняют
файлы для диагностики. Контролируйте свободное место и не удаляйте активные каталоги.
Кэш обложек имеет тот же срок. Медиа-узлы получают запросы без cookies и credentials;
HTTPS, DNS/IP и redirects проверяются отдельно от парсера.

Бот автоматически сообщает завершение, конечную/блокирующую ошибку и необходимость
решения. Обычные шаги/повторы не рассылаются. Inbox, изменения предметных данных и
outbox ответа фиксируются вместе. Неоднозначная доставка самого уведомления не
повторяется автоматически и никогда не меняет успешную публикацию; проверьте `/status`.
Успешно отправленные payload outbox стираются, включая одноразовые коды сопряжения.
Не публикуйте `.env`, `secrets`, cookie jar, полный дамп БД или сетевые debug traces.

```sh
uv run --locked --extra source ehtg backup /private/backup-new.sqlite3
```

Храните backup вне сервера. Отдельно и защищённо сохраняйте `.env`/сессию. Для
восстановления остановите процессы, восстановите согласованную SQLite-копию и
необходимые каталоги файлов, запустите миграции и процессы. Незавершённые файлы
перепроверяются; оставшиеся `sending` требуют ручной сверки. Для обновления сначала
сделайте backup: старый бинарник отклоняет более новую схему, поэтому откат требует
восстановить совместимую копию БД, а не менять хеши уже применённых миграций.

## Что проверяется отдельно в рабочем окружении

Cookies, актуальный HTML/медиа-узлы, доступность аккаунта с IP VPS, права и настоящая
доставка в отдельный тестовый канал; исполнение Linux-лимитов и работа рядом с VPN;
свободные порты, HTTPS и продление сертификата. Локальные синтетические тесты этих
проверок не заменяют. Команды выше подготовлены для администратора; они не запускались
на VPS при разработке.
